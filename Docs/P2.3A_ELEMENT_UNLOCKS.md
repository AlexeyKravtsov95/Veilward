## 1. Scope, acceptance и источники

Цель P2.3: Domain определяет доступность шести существующих типов, игрок принимает два необратимых решения внутри одного восьмиволнового забега, UI объясняет требования, checkpoint сохраняет решения без повторной выдачи. Acceptance: реальный старт с 150 Gold; точные фазы/отказы; Steam/Storm доступны в объяснимые моменты; повторные команды и Continue не создают ресурсов; миграция не выдумывает историю. Риски: поздняя синергия, слабый старт, failed save на границе награды, неоднозначные schema 1/2, подмена исторического replay новым production evidence.

Прочитаны [AGENTS](../AGENTS.md), [GDD](GDD.md), [TECH_DESIGN](TECH_DESIGN.md), [ROADMAP](ROADMAP.md), [BACKLOG](BACKLOG.md), [README](../README.md), `ProjectSettings/ProjectVersion.txt`, спецификации и планы [P2.1](P2.1A_ELEMENTAL_TOWERS.md)/[P2.2](P2.2A_REACTIONS.md). Обязательные файлы присутствуют. Проверены Domain commands/catalog/phases, config factory, MainMenu/session и checkpoint pipeline. При расхождении исторического описания с saved data ниже приведены фактические значения базы.

**Вне scope:** кампания и её постоянные unlocks, сектора/расширение карт, способность/босс P2.4, WILDFIRE/MAGMA/MIRE/SAND и их реакции, массовый арт, packages/Unity upgrades, перерасчёт существующих цен/урона/награды. ART.1.1 технически влит, художественное утверждение владельца и physical device QA открыты. G2/баланс/TestFlight/release не закрываются.

## 4. Старт и экономика

New Game создаёт Preparation волны 1 (`waveIndex = 0`, tick 0), HP **20**, Gold **150**, нет башен/врагов, earned/spent **0/0**, `pendingChoiceId = start-resonance`, открытых элементов пока нет. Модальный выбор предлагает FLAME и GALE, изначально ни один не выбран. Tap выбирает только preview. Отдельный Confirm отправляет Domain `ChooseElementCommand(start-resonance, flame|gale)`, открывает ровно один элемент и очищает pending; старт не расходует межволновой выбор. Cancel очищает preview, оставляя обязательный выбор; можно выйти в меню. Сменить подтверждённый резонанс можно только через New Game/reset, а не Sell/Continue.

После Confirm обычная Preparation; постройка и Start разрешены по прежним правилам. Проверка **доступного бюджета**, без денег из будущих волн:

| Старт | Реально открытая покупка L1 | Возможное размещение при 150 | Остаток |
|---|---:|---|---:|
| FLAME | 70 | 1 FLAME либо 2 × FLAME = 140 | 80 либо 10 |
| GALE | 80 | 1 GALE = 80; вторая стоит ещё 80 и отклоняется | 70 |

TIDE **60**, STONE **90**, STEAM/STORM **110**: цена сама по себе не даёт права построить закрытый тип. Не использовать скрытый test-tower для обхода стартового ограничения. Start не требует обязательной башни (сохраняется старое правило); осознанный старт без обороны возможен только после выбора резонанса. Возможность купить оборону и начать матч доказуема арифметически; выживание до первой награды/победа с обоими стартами **ещё не проверены**. Проверить естественные результаты в P2.3e, не повышая Gold и не меняя баланс для зелёного теста.

Резонанс — выбор доступного набора строительства, а не damage affinity или кампания. New Game всегда сбрасывает его и прогресс. Полный refund не даётся: обычная продажа `floor(InvestedGold × 70 / 100)`, без возврата открытия. Награды committed EightWave: counts **5/6/7/8/9/10/11/12**, **5 Gold/kill**, **20 Gold/completed wave**. Shared Shade Armor **0**, HP 100. Значения сверены с `git show 4ff11b5:Assets/_Game/Configs/EightWave.asset` и `TestWave.asset`, вне временных мутаций test fixtures. P2.3 их не меняет и не переносит в код.

## 5. Межволновое решение, атомарность и фазы

Choice IDs: `after-wave-3`, `after-wave-6`; option IDs: `flame`, `tide`, `gale`, `stone`, только ещё закрытые. Порядок карточек FLAME/TIDE/GALE/STONE; после стартового выбора у первого reward три варианта, у второго два. Ни RNG, ни campaign unlocks. Новый unlock открывает базовый тип и каждый гибрид, чьи два requirements теперь выполнены; не создаёт башню/Gold/Upgrade. Одно и то же изменение не выдаёт отдельную награду за гибрид.

В `Step()` после Death/Removal: если HP 0 — Defeat, выбора/bonus нет. Иначе при завершении всех spawns и enemies: существующий Gold bonus один раз, фаза WaveComplete (Victory на 8), затем на волнах 3/6 один earned choice + pending, **до Export/save/возврата управления UI**. Step вне Combat ничего не начисляет. Дополнительного completion callback, который может повторно выдать выбор, нет.

| Состояние | Разрешено | Отклоняется без mutation | Следующее состояние |
|---|---|---|---|
| Preparation 1, pending start | Preview/Cancel, Confirm ровно FLAME/GALE, Pause/выход | Place/Upgrade/Sell, Start/Next, wave-choice ID | Confirm → Preparation 1, один unlocked, pending none |
| Preparation N, pending none | Place/Upgrade/Sell и Start с прежними проверками | ChooseElement, Next | Start → Combat N |
| Combat N | Только fixed Step/read-only inspector/Pause | ChooseElement, economy, Next, repeated Start | Успешное окончание → строка ниже; lethal → Defeat |
| WaveComplete 1/2/4/5/7 | Next (Gold уже начислен), read-only | Economy, ChooseElement, Start | Next → Preparation N+1 |
| WaveComplete 3/6, pending | Preview/Cancel, Confirm одного закрытого элемента, Pause/выход | Next → `RejectedPendingElementChoice`; Start invalid phase; economy invalid phase | Confirm остаётся WaveComplete той же волны, spent +1, pending none |
| WaveComplete 3/6, pending none | Next | Повторный Confirm, economy, Start | Next → Preparation 4/7; отдельный Start |
| Victory 8 / Defeat N | Просмотр/меню/New Game | Все gameplay commands/Step | Terminal checkpoint, Combat Continue невозможен |

`ChooseElementCommand` содержит ожидаемый choice ID, а не просто элемент. Domain проверяет mode, phase, точное совпадение pending ID, вариант, отсутствие уже открытой стихии, доступный earned credit. Проверки все выполняются **до** публикации нового progression. Успех синхронно открывает элемент, добавляет один spent record, увеличивает spent count, очищает pending; ни HP/Gold/Kills/tick/IDs/Grid/towers/events, ни waveIndex не меняются. Start подтверждается аналогично, но без earned/spent. Повтор success-command (даже для другого option), старый ID на втором reward, unknown/default/null ID, open-element option и stale UI confirm — отказ. Нет автоматического выбора и no-op success, скрывающего отсутствие эффекта.

Отказы выбора: `InvalidPhase`, `ProgressionDisabled`, `NoPendingChoice`, `ChoiceMismatch`, `InvalidOption`, `AlreadyUnlocked`, `NoChoiceCredit`. Приоритет: phase → mode → нет pending → mismatch → неизвестный/недопустимый option → already unlocked → credit; start допустим только в Preparation 1, wave ID только в WaveComplete своей волны. Ошибка сохраняет полный snapshot, включая события. Enum BattlePhase **не меняется**, новые enum failure values добавляются в конец с сохранением старых значений.

**Pause/modal boundary:** Pause выше всех окон, freeze simulation/VFX без catch-up. Он очищает локальный preview и подтверждение, но **не удаляет Domain pending/earned**; Resume возвращает обязательный выбор без выбранной карточки и подавляет world pointer текущего кадра. Sell/inspector/placement не могут одновременно владеть вводом с выбором. Чужой modal блокирует Confirm выбора; окно выбора допускает только свой Confirm/Cancel/Pause/выход. Все внешние API SceneController/Placement и кнопки проходят одинаковый guard; прямой `.onClick.Invoke` не обходит его. Paused/modal rejection не обращается к Domain, не пишет save. Domain отдельно валидирует phase/pending/requirements: выключенные кнопки не защита правил. Чистый Domain не читает Unity focus/Canvas и не обещает отклонять прямой test-вызов из-за не переданного UI-состояния.

## 6. Доступность башен и объяснения

| TowerDefinitionId | Required unlocked elements | L1 price |
|---|---|---:|
| flame | Flame | 70 |
| tide | Tide | 60 |
| gale | Gale | 80 |
| stone | Stone | 90 |
| steam | Flame **и** Tide | 110 |
| storm | Tide **и** Gale | 110 |

Requirements относятся к архетипу на всех L1–L3, не к localized name, StatusKind, наличию компонентов на поле или порядку размещения. Нельзя выводить их автоматически из status/intrinsic: это явные validated данные. Hybrid покупается отдельно, обе базовые башни строить/объединять не нужно. Реакция status pair по-прежнему требует фактических попаданий; открытие пары только даёт возможность построить соответствующие башни. Intrinsic использует существующий resolver без добавления статусов/второй награды.

- **Place:** phase → pending → known type → требования → прежние bounds/blocked/occupied/Gold/ID checks. Новые отказы `PendingElementChoice`, `ElementLocked`; test-tower в новом mode → `LegacyTowerUnavailable`. Closed type не списывает деньги и не занимает клетку даже через прямую Domain-команду. Hidden legacy type не становится бесплатным обходом.
- **Upgrade:** phase → pending → TowerId → требования его типа → прежние MAX/overflow/Gold. Без conversion в гибрид; TowerId/cell/NextAttackTick сохраняются. Locked army в новом mode не должна пройти Restore; дополнительный `ElementLocked` guard защищает invariant. Старый all-open mode сохраняет Upgrade существующих test-tower/гибридов.
- **Sell:** phase → pending → прежние ID/grid/refund. Не требует повторного открытия, не закрывает стихию и не возвращает выбор. Повторный Sell → TowerNotFound, без выплаты; новый TowerId при rebuild. Все типы имеют прежнюю экономику.

`ShowInCatalog` означает видимость, **не разрешение**. UI оставляет все шесть карточек в прежнем порядке, закрытые с замком, именами недостающих элементов и ценой. Их tap открывает только read-only описание требований без world build preview/Confirm. Например: «STEAM: нужны Пламя и Прилив. Не открыт Прилив; следующий выбор после волны 3». После второго выбора: «Новых выборов в этом забеге больше нет». При открытии обоих: «Доступна; цена 110 Gold», отдельно «Недостаточно Gold» если требуется. Выбранная доступная карточка повторно проверяется Domain при Confirm. Не смешивать unknown type, locked и insufficient gold в одно объяснение. Полный availability query использует те же проверки, что command, и возвращает missing elements + причину; Presentation не дублирует requirements.

## 7. Временная диаграмма всех восьми волн

Вариант A: старт FLAME → после 3 TIDE → после 6 GALE. Вариант B: старт GALE → после 3 TIDE → после 6 FLAME. Оба — гипотезы стратегии, не обещание Victory.

| Боевая волна | Earned/spent перед Start | A: открыто / потенциально доступно | B: открыто / потенциально доступно | После успешного окончания |
|---|---|---|---|---|
| 1 | 0/0 | Flame; без Steam/Storm | Gale; без Steam/Storm | Нет выбора |
| 2 | 0/0 | То же | То же | Нет выбора |
| 3 | 0/0 | То же | То же | WaveComplete 3: earned 1, pending; Confirm Tide → 1/1 |
| 4 | 1/1 | Flame+Tide; **Steam pair + STEAM** | Gale+Tide; **Storm pair + STORM** | Нет выбора |
| 5 | 1/1 | То же | То же | Нет выбора |
| 6 | 1/1 | То же | То же | WaveComplete 6: earned 2, pending; Confirm Gale/Flame → 2/2 |
| 7 | 2/2 | Flame+Tide+Gale; **обе пары и оба гибрида** | То же | Нет выбора |
| 8 | 2/2 | То же; Stone закрыт | То же | Victory, без третьего выбора |

Доступность открывается сразу при Confirm в WaveComplete, **покупка только в Preparation 4/7**, первая возможная атака — в Combat 4/7. Обе реакции не могут произойти в волнах 1–3 нового забега. Обе пары требуют три элемента, поэтому одновременно возможны лишь с волны 7 при пути к Flame+Tide+Gale. Выбор Stone после 3 или 6 осознанно оставляет максимум одну пару; Flame+Gale без Tide не даёт ни одной из этих реакций. При отказе от Tide во всех выборах обе реакции недоступны весь матч. Поздняя double-synergy (только две волны) — риск U-01/U-02; не переносить награды молча для исправления баланса.

Это **временной допуск**, не гарантия Gold/попаданий/proc. STEAM/STORM требуют по 110 Gold; две базы Flame+Tide стоят 130, Tide+Gale — 140, три базы — 210, оба гибрида — 220, всё вместе — 430. Например, A: одна стартовая FLAME за 70, остаток 80; если первые три волны полностью убиты, доход `18 × 5 + 3 × 20 = 150`, перед Preparation 4 Gold 230, TIDE+STEAM стоят 170, остаётся 60. При двух стартовых FLAME без иных операций Gold был бы 160: на TIDE+STEAM сразу не хватает 10, вторую покупку Domain отклоняет. Открытие не компенсирует этот дефицит. Это условная верхняя оценка дохода, **не выполненный replay**. В P2.3e отдельно доказать реальный command script с каждым стартом, положительные procs обоих видов к 7/8 и доступные покупки без seed/save/Gold подмены. Если saved match не даёт coverage, честно записать достигнутый префикс/Defeat и запросить отдельное баланс-решение; synthetic fixture может доказать правила, но не подменить production coverage.

## 8. Сохранения: schema 3 и строгая validation

### 8.1 Поля и инварианты нового mode

`BattleCheckpoint` получает обязательный вложенный `elementProgression`; schema 3 не принимает его отсутствие. Ни один отсутствующий enum/int default не должен превращать malformed JSON в new game. Строковые IDs/обязательные arrays проверяются явно. Предлагаемая форма вложенного объекта после волны 3, до Confirm:

```json
{
  "rulesId": "wave-unlocks-v1",
  "startResonanceId": "flame",
  "unlockedElementIds": ["flame"],
  "choicesEarned": 1,
  "choicesSpent": 0,
  "spentChoices": [],
  "pendingChoiceId": "after-wave-3"
}
```

`spentChoices` — упорядоченные `{ "choiceId": "after-wave-3", "elementId": "tide" }`; максимум два. `startResonanceId = unselected` и `pendingChoiceId = start-resonance` до стартового Confirm; отсутствие pending кодируется **строкой `none`**, не missing/null. Element IDs перечисляются в canonical Flame/Tide/Gale/Stone order. Domain state read-only, Export делает deep copy.

Число успешно завершённых волн `C`: Preparation/Defeat → `waveIndex`, WaveComplete → `waveIndex + 1`, Victory → 8. Combat не сериализуется. Для `wave-unlocks-v1`:

- `choicesEarned == (C >= 3 ? 1 : 0) + (C >= 6 ? 1 : 0)`; `choicesSpent == spentChoices.Length`, `0 <= spent <= earned <= 2`. Count не выдаётся повторно при restore.
- История — точный prefix `after-wave-3`, затем `after-wave-6`, без duplicate ID/element, с ещё закрытым на тот момент элементом. Нет усилений/credit exchange. `unlockedElementIds` в точности равен старту + истории; unknown/duplicate/missing/лишний элемент invalid.
- До стартового Confirm только начальная Preparation 1, tick 0, начальные HP/Gold/Kills/IDs, пустая армия/история/earned и pending start. Подтверждённый старт строго flame/gale. В иных состояниях unselected invalid.
- Неизрасходованный credit допустим **только** в WaveComplete 3/6: ровно один, pending совпадает с этой волной. Во всех Preparation после первой и terminal все заработанные выборы потрачены, pending none; WaveComplete 3/6 после Confirm также earned=spent/pending none. Нельзя восстановить Preparation 4 с непотраченным reward 3 или Victory с pending 6.
- Каждая башня нового mode удовлетворяет своим requirements, legacy test-tower запрещён. Все прежние scalar/phase/grid/ID/level/investment проверки сохраняются, включая positive HP и ограничения terminal.
- Неизвестные rules/content/schema, невозможная комбинация полей, negative/overflow counts, out-of-order история отклоняются целиком до mutation State/Grid/events. Не «чинить» extra unlocks и не угадывать недостающие записи. JsonUtility без presence metadata не доказывает наличие нулевого поля: в реализации проверить обязательные keys до materialization либо использовать sentinel DTO и presence validation; тестировать именно missing keys, а не только неверные значения.

### 8.2 Точки сохранения и поведение при прерывании

Сохраняются те же safe phases и прежние physical slots `wave-checkpoint-v1.json`, `.tmp`, `.bak`; имя не равно schema. Ни enemies/statuses/reaction cooldown, ни UI preview/selected card не сериализуются. Pending — часть Domain, а не UI transient.

| Событие/сбой | Live и disk contract |
|---|---|
| New Game, до выбора старта | После прежнего recovery-safe reset сохранить initial pending snapshot; failed initial save оставляет live pending и error, Start блокируется до успешного save. До первого успешного save disk Continue может отсутствовать. |
| Завершена 3/6, ещё нет Confirm, выход | Сначала сохранить WaveComplete с bonus/earned/pending. Успешный save → Continue открывает тот же выбор без выбранной карточки, без нового bonus/credit. |
| Confirm принят, выход | Немедленный SaveCurrentState после успешной Domain-команды, хотя phase не менялась. Успешный save → тот же unlocked/history, pending none; Continue не требует выбрать заново. |
| Save после bonus/Confirm/Build/Next failed | Успешная live Domain mutation **не откатывается**, ошибка «не сохранено; после выхода возможен откат». Предыдущий durable checkpoint/backup остаётся; UI даёт Retry Save. **Next и Start блокируются в orchestration**, пока SaveCurrentState текущего safe snapshot не успешен. Новый выбор не повторяется при Retry. Domain остаётся независимым от filesystem. |
| Exit после failed Confirm save | Если disk содержит pending, он вернётся; можно выбрать другой вариант, но никакая часть неподтверждённой disk-версии не переносится в restored state. Если disk старее Combat, повторяется вся волна со старым HP/Gold/Kills. Это полный rollback, а не вторая награда поверх live. Гарантия durability после failed save не заявляется. |
| Interrupted Combat 4/7 | До Start успешно сохранить Preparation с уже выбранными unlocks/history. Rollback убирает всю попытку (kills/Gold/HP/IDs/events/statuses), но сохраняет подтверждённые до Start открытия; pending none. Нельзя сохранить/restore Combat наполовину. |
| Repeated Continue/Load/Next/Confirm | Load/Restore без выдачи rewards и записи bytes. Next только WaveComplete→Preparation один раз; после failed Next save следующая волна блокируется до durable Preparation. Старый Confirm никогда не расходует второй credit, даже после волны 6. |
| Pause/background в pending | Preview сброшен, pending сохраняется. Фон не подтверждает автоматически и не создаёт новый reward; Resume без catch-up. |
| Повреждённый primary, валидный backup | Независимо decode→migrate→validate каждый слот; выбрать первый валидный, показать backup warning. Восстановить **весь** backup, не объединять unlocks primary с экономикой backup. Backup может быть старее/другого mode; его правила выбираются целиком. |

Перед Next/Start orchestration сначала запрашивает Domain read-only eligibility (phase/pending и прежние ограничения перехода). При отказе save и mutation не выполняются. Для допустимого Next сохранить текущую WaveComplete, затем вызвать Domain Next и сохранить Preparation; для допустимого Start — успешный safe save Preparation, затем Start. Так невалидные команды не пишут checkpoint. Retry Save — отдельное persistence-действие, оно не вызывает Choose/Next/Step. В direct Battle без session остаётся изоляция от реального disk; тот же progression/Domain contract, отсутствие durability явно отмечено. Ошибка сохранения terminal показывается; terminal не становится Continue-able.

### 8.3 Явная миграция schema 1/2 и content routing

Новый обязательный progression с историей меняет форму и смысл snapshot: bump schema **2→3 необходим**. Новый content ID **`eight-wave-unlocks-v1`** необходим для новых progression constraints; прежний `eight-wave-v1` означает all-open semantics, а не обещание идентичного боя между версиями. Не менять IDs существующих башен/цен. Schema 3 старым binary не читается; downgrade не поддерживается, fallback на совместимый backup возможен по старым правилам.

| Вход | Разрешённое преобразование и проверка |
|---|---|
| Schema 1 + `eight-wave-v1` / `legacy-single-wave-v1` | Проверить старые safe-state ограничения; deep copy каждой башни строго в test-tower (как существующий v1 migrator), сохранить все scalar/economy/ID/cell/cooldown. Затем общий all-open migration и current validation. Никакого mapping в FLAME. |
| Schema 2 + один из этих **точных** старых IDs | Сохранить точный тип/уровень/инвестиции каждого tower, включая STEAM/STORM и смешанную армию, без Sell/refund/conversion. Добавить `rulesId = legacy-all-open-v1`, `startResonanceId = legacy`, все четыре unlocked, earned/spent 0/0, пустую историю, pending none. Не выдавать «пропущенные» награды 3/6. |
| Schema 3 + старый ID | Только `legacy-all-open-v1` с точно указанными legacy значениями, прежней wave count/map/investment validation. Все четыре остаются открыты и после Sell последней башни. No pending/выборов во всём оставшемся матче; UI подписывает «Продолжение по прежним правилам». |
| Schema 3 + `eight-wave-unlocks-v1` | Только `wave-unlocks-v1` и все инварианты §8.1. Native save с test-tower либо лишним unlock invalid. |
| Schema 1/2 + новый ID, unknown ID/schema/rules, missing type в v2, invalid старый state | Отказ без publication; затем независимо backup. Не дополнять default fields и не переименовывать content автоматически. |

Legacy-single-wave остаётся одноволновой совместимостью и test path; не получает after-wave-3/6. Только EightWave New Game использует новый mode. Старый EightWave продолжает те же сохранённые волны, counts/награды/definitions, доступные текущей версии; **не обещаем исторический outcome** из-за уже изменённых до P2.3 configs. Unknown/изменённые цены с несоответствующим InvestedGold — отказ, не price migration.

Миграция только в памяти и idempotent: повторные Load дают один и тот же результат, bytes primary/backup не меняются. Следующий successful Save пишет schema 3 **с прежним ID в legacy mode**, temp validate + atomic replacement + предыдущий валидный backup. Fail оставляет читаемый старый слот; invalid primary не вытесняет valid backup. New Game reset сохраняет существующее recovery поведение и не трогает будущий campaign save.

Существующая цепочка exact equality должна быть расширена **явным whitelist compatibility adapter**, общим для Store, MainMenu factory и CheckpointController: запрошенный новый EightWave разрешает родной новый ID или ровно старый EightWave; одноволновый ID не принимается за EightWave. Нет общего «принимать любой content». Выбор validated simulation/rules происходит до восстановления, old ID сохраняется; Restore controller больше не может просто сравнить envelope ID с New Game ID. Валидация источника выполняется до normalization, нормализованного результата — перед публикацией. Иначе schema 2 гибридный backup может быть ошибочно отвергнут новым pending invariant или принять новые правила без истории.
