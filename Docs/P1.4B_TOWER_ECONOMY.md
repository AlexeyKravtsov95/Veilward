# P1.4b — Tower Economy: техническая спецификация

## Scope и acceptance criteria

Реализуется один вертикальный путь для существующей Test Tower: выбор построенной башни, два платных улучшения, продажа с подтверждением, освобождение клетки и повторное строительство. Сохраняются P1.1–P1.4a, текущие награды, восьмиволновой матч, Unity/URP/packages и graybox-дизайн.

Готовый тикет должен обеспечить:

- сериализованные уровни 1/2/3: Damage 25/35/50, Range 3, FireRate 2, стоимость 60/50/80 и InvestedGold 60/110/190;
- атомарные Domain-команды `UpgradeTower(TowerId)` и `SellTower(TowerId)` только в Preparation с явными результатами;
- refund `InvestedGold * 70 / 100` в целочисленной long-арифметике: 42/77/133;
- сохранение TowerId, координаты и NextAttackTick при upgrade; монотонные ID после sell/rebuild;
- выбор occupied cell в Preparation и просмотр характеристик в Combat без экономических действий;
- недоступный Upgrade при max level/недостатке Gold и отдельное подтверждение Sell;
- удаление Tower View после продажи, повторное размещение и отсутствие атак от проданной башни;
- положительные полные static, EditMode, PlayMode и `git diff --check`, реальные Play Mode screenshots.

## Затронутые системы и риски

- Domain: уровни TowerDefinition, TowerState, BattleSimulation, BattleState, BattleGrid и результаты команд.
- Configuration: существующие serialized поля Level 1 плюс serialized Level 2/3 в TestWave, наследуемые EightWave через sharedScenario.
- Presentation: существующий BattlePlacementController, BattleSceneController и HUD; UI только вызывает Domain API.
- Editor: BattleSceneBuilder и BattleAssetValidator для новых панелей, кнопок и обязательных ссылок.
- Tests/docs: REG-BATTLE-025…050, serialized config, scene validation/reproducibility и PlayMode flow.
- Риски: повторный refund, отрицательный/переполненный Gold или InvestedGold, сброс cooldown, атака удалённой башни, stale selection/view и ложный visual PASS.

## Domain contracts

`TowerDefinition` остаётся immutable описанием одного уровня. `BattleSimulation.TowerLevels` содержит упорядоченные определения; прежний `TowerDefinition` обозначает Level 1 для обратной совместимости. `TowerState.Level` одно-based, `InvestedGold` равен сумме покупки и успешных upgrades, `Definition` меняется только при успешном upgrade.

Upgrade сначала проверяет Preparation, TowerId, наличие следующего уровня, affordability и `InvestedGold + next.Price <= int.MaxValue`. Затем одна атомарная операция списывает цену, меняет Definition/Level/InvestedGold. NextAttackTick не записывается. Повторный вызов покупает следующий уровень только при наличии средств; max level и любые ошибки не меняют состояние.

Sell проверяет Preparation, TowerId и принадлежащую башне Occupied cell. Refund вычисляется заранее как `(int)((long)InvestedGold * 70 / 100)`. Затем башня удаляется, клетка освобождается через internal `BattleGrid.TryRelease`, refund начисляется через saturating Credit. Повторные Sell/Upgrade для удалённого ID возвращают TowerNotFound. ID не переиспользуются.

`BattleGrid.TryRelease` доступен только внутри Domain и возвращает false для outside-map, Available и Blocked. Presentation не получает mutation API для Grid, Gold или TowerState.

## UI contract

Available cell сохраняет placement preview и Confirm/Cancel. Occupied cell выбирает существующую башню: highlight и range показываются, placement preview скрыт. Tower Panel отражает Domain Level, Damage, Range, FireRate, следующий Upgrade cost и текущий Sell refund.

Upgrade вызывает `UpgradeSelectedTower`; Sell сначала открывает confirmation и сохраняет pending TowerId. `ConfirmSellSelectedTower` разрешает операцию только при активном confirmation и совпадении SelectedTowerId с pending ID; bypass и подтверждение другой башни возвращают ConfirmationRequired без изменения Gold/Grid. Пока диалог открыт, Upgrade, повторный Sell, placement Confirm/Cancel и Start/Next Wave заблокированы в API и кнопках. Cancel скрывает confirmation, очищает pending ID и восстанавливает действия без изменения Domain. Смена selection отменяет прежнее confirmation. В Combat панель остаётся доступной для чтения, но Upgrade/Sell/confirmation actions заблокированы. После успешной продажи selection и панели очищаются; BattleSceneController удаляет соответствующий View и больше не использует его для AttackEvents.

## Regression и evidence

REG-BATTLE-025…050 фиксируются до реализации. Полный snapshot включает фазу, tick/wave, HP/Gold/Kills, enemies, towers с Level/InvestedGold/stats/cooldown, grid и AttackEvents. Deterministic матч с Upgrade/Sell выполняется дважды и сравнивает timelines. Отдельные EditMode/PlayMode tests покрывают bypass, modal blocking, Cancel, TowerId binding, успешную продажу и read-only Combat stats; scene measurement выполняется на временном экземпляре в preview scene и не изменяет сохранённую Battle scene.

Обязательные команды: `./Scripts/run-static-checks.sh`, `./Scripts/run-edit-mode-tests.sh`, `./Scripts/run-play-mode-tests.sh`, `git diff --check`. Evidence должны содержать реальные кадры выбора L1, L2, L3, подтверждённой продажи/refund, повторной постройки и атаки улучшенной башни. Полный визуальный Victory фиксируется только при достижимости без изменения баланса. Физический iPhone не объявляется проверенным без device-теста.

## Known base limitation

P1.4a ещё не merged в `main` на момент старта. Ветка P1.4b создаётся от reviewed P1.4a HEAD как stacked change; самостоятельный merge или перенос базового тикета не выполняется.
