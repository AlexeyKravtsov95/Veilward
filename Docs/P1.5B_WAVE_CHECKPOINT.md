# P1.5b — Wave Checkpoint & Continue: техническая спецификация

## Scope и acceptance criteria

P1.5b начинается от `origin/main` с merged PR #11 (`786095d`). Реализуется один вертикальный путь: версионированный checkpoint волны, восстановление новой сессии через существующий MainMenu и минимальные New Game / Continue. Сохраняются текущие 30 Hz симуляция, баланс EightWave, команды, Pause & Background и graybox-стиль.

Готовый тикет должен обеспечить:

- checkpoint после успешных Build, Upgrade и Sell в Preparation; rejected commands, Cancel и presentation selection не создают новый checkpoint;
- обязательное успешное сохранение полной Preparation непосредственно перед Start Wave;
- восстановление прерванного Combat в Preparation той же волны с откатом HP, Gold, kills, towers, cooldown и следующих Enemy/Tower IDs к началу попытки;
- сохранение WaveComplete после начисления награды, новой Preparation после Next Wave и terminal Victory/Defeat без повторных наград или автоматического запуска волны;
- явные Domain export/restore API с полной валидацией до публикации состояния;
- schema version, scenario/content ID, атомарную замену, предыдущий проверенный backup и понятную диагностику ошибок;
- Continue только для корректной незавершённой сессии, fallback на совместимый backup и явный New Game;
- recreation views из Domain state и очистку selection, confirmation, beams и pause boundary после scene/session restore;
- regression tests, положительные quality gates и реальный Play Mode flow MainMenu → Battle → checkpoint → перезагрузка сцены → Continue.

Вне scope: mid-Combat resume с активными enemies, RNG (в текущей симуляции отсутствует), миграции неизвестных будущих версий, iCloud, шифрование, новые игровые механики, редизайн UI, новые packages и физический device-test без устройства владельца.

## Рассмотренные подходы

1. **Safe-wave snapshots — выбран.** Domain экспортирует только Preparation, WaveComplete и terminal. Combat не сериализуется: последняя Preparation восстанавливается до Start Wave. Это точно соответствует откату незавершённой попытки и не требует сериализации enemies/spawn schedule.
2. Полный mid-Combat snapshot потребовал бы enemy HP/distance, spawn index, RNG и дополнительных инвариантов; это другой игровой контракт и не входит в задачу.
3. Reflection/автосериализация всего `BattleSimulation` отклонена: она смешивает Domain с хранилищем, сохраняет ненужные internals и не гарантирует валидацию/совместимость.

## Затронутые системы и риски

- Domain: `BattleSimulation`, `BattleState`, `TowerState`, новые immutable checkpoint DTO и validation results.
- Configuration: стабильный `scenarioContentId` у `BattleScenarioConfig`; несовместимые изменения контента обязаны сменить ID отдельным решением.
- Infrastructure: JSON serialization, versioned local file, atomic replace, backup и load diagnostics.
- Application/Presentation: session handoff, checkpoint orchestration, Battle lifecycle, MainMenu New Game / Continue.
- Editor: воспроизводимая генерация MainMenu/Battle wiring и validation serialized references.
- Tests/docs/evidence: REG-BATTLE-067…088, isolated temporary directories, Play Mode screenshots и sanitized example JSON.
- Риски: двойная награда, reuse проданного TowerId, публикация частично восстановленного Grid/State, перезапись исправного primary повреждённым backup, скрытая потеря предыдущего save при IO error, запись тестов в реальный `persistentDataPath` и ложный visual PASS.

## Domain checkpoint contract

`BattleSimulation.ExportCheckpoint()` допускает только Preparation, WaveComplete, Victory и Defeat. Возвращается глубокая независимая копия следующих данных:

- `phase`, `waveIndex`, `tick`, `baseHealth`, `gold`, `kills`;
- `nextEnemyId`, `nextTowerId`;
- для каждой башни: `towerId`, `x`, `y`, `level`, `investedGold`, `nextAttackTick`.

`WaveCount`, Path, Enemy/TowerDefinition и характеристики уровней не сериализуются: они восстанавливаются из совместимого проверенного scenario. Enemy states и spawn counters не сериализуются. При восстановлении `_nextSpawnIndex = 0`; успешный Start Wave заново задаёт `_waveStartTick = tick`. В terminal active enemies не восстанавливаются и не создаются: симуляция терминальна, Step остаётся no-op.

`BattleSimulation.TryValidateCheckpoint(checkpoint, out error)` не меняет текущую симуляцию. `RestoreCheckpoint(checkpoint)` использует ту же проверку и публикует новые `State`/`Grid`, counters и пустой AttackEvents только после полного успеха. Combat, неизвестные enum phases и любые нарушения отклоняются:

- отрицательные tick/HP/Gold/kills/InvestedGold/NextAttackTick, HP выше configured initial health, некорректный WaveIndex;
- неположительные/дублирующиеся TowerId, next IDs, допускающие reuse существующих ID; `nextEnemyId/nextTowerId = int.MaxValue` также invalid и при load вызывает fallback на валидный backup;
- дубли/outside-map/blocked cells и несогласованная Grid occupancy;
- Level вне configured range и InvestedGold, не равный сумме configured цен до этого уровня;
- Preparation/WaveComplete с нулевым HP, Victory не на финальной волне или с нулевым HP, Defeat с HP выше нуля;
- WaveComplete после финальной волны неlegacy scenario.

Проданные ID не сохраняются списком: монотонность обеспечивается `nextTowerId > max(existingTowerId)`. После restore новая постройка использует сохранённый next ID. Атрибуты башни берутся только из `TowerLevels[level - 1]`; serialized Damage/Range/FireRate отсутствуют. Значение `int.MaxValue - 1` — безопасный exhaustion boundary: последний выделенный ID не превышает `int.MaxValue - 2`, поэтому stable checkpoint остаётся валидным. При недостатке оставшихся Enemy IDs Start Wave возвращает `RejectedIdExhausted` до смены фазы; исчерпанный Tower counter возвращает `PlaceTowerFailureReason.IdentifierExhausted` без Gold/Grid mutation.

## Save envelope и совместимость

Infrastructure сериализует JSON envelope:

- `schemaVersion`: текущее значение **1**, принимается только точное совпадение;
- `scenarioContentId`: стабильный идентификатор конкретного scenario и совместимого баланса, сравнение Ordinal;
- `state`: Domain checkpoint DTO.

Для текущих assets задаются `legacy-single-wave-v1` и `eight-wave-v1`. Неизвестная schema version и другой content ID — explicit incompatible result, а не попытка угадать миграцию. Повреждённый JSON, null state и failed Domain validation — invalid/corrupt result. Ни один несовместимый файл не запускает Battle Continue.

## Файловое хранилище

Runtime root — `Application.persistentDataPath`; файлы: `wave-checkpoint-v1.json`, `wave-checkpoint-v1.json.bak`, `wave-checkpoint-v1.json.tmp`. Тесты и QA используют изолированную временную директорию.

Save выполняется в одной директории:

1. Сериализовать envelope, создать/перезаписать temp и выполнить `Flush(true)`.
2. Перечитать temp и повторно проверить schema, content ID и Domain checkpoint.
3. Если существующий primary проходит ту же проверку, `File.Replace(temp, primary, backup)` атомарно заменяет primary и сохраняет предыдущий корректный primary как backup.
4. Если primary отсутствует, использовать `File.Move(temp, primary)`. Если primary повреждён/несовместим, атомарно заменить его без обновления backup, чтобы не перезаписать последний корректный backup повреждёнными данными.

Load проверяет primary, затем backup. Совместимый незавершённый backup разрешает Continue даже при повреждённом/обрезанном primary. Возвращаются явные statuses: missing, loaded primary, loaded backup, incompatible, corrupt и IO error. Сообщения UI не содержат приватных paths; техническая diagnostics пишется в Console.

При ошибке записи temp/replace текущая симуляция продолжается, прежний primary/backup не удаляются, а Battle показывает `Save failed — previous checkpoint kept.` Build/Upgrade/Sell не откатываются в live-симуляции. Start Wave не вызывается, если предварительный save не удался; Domain state остаётся Preparation, отображается `Start Wave requires a successful checkpoint save.` Повторная попытка разрешена после устранения ошибки.

New Game — только явный click. Перед запуском сначала удаляется temp, затем primary и backup последним. Если temp cleanup завершился ошибкой, primary/backup остаются байт-в-байт, fresh session не создаётся, Battle не открывается, а прежний Continue остаётся доступным. При ошибке удаления primary Battle также не открывается и показывается diagnostics; backup удаляется только после успешного удаления primary. Первый новый Battle сразу пытается сохранить начальную Preparation.

## Session и lifecycle

`BattleSessionContext` передаёт между сценами только store, content ID и выбранный envelope для Continue. MainMenu создаёт context для New Game или Continue. Battle проверяет совпадение content ID, восстанавливает Domain до первой синхронизации views и очищает accumulator/pause boundary. Прямой запуск сохранённой Battle без MainMenu context остаётся изолированным test mode: новая in-memory симуляция без чтения/записи реального checkpoint.

Disk restore выполняется только при входе в новую Battle session. Существующие `BattlePauseController.OnApplicationPause/OnApplicationFocus` по-прежнему управляют только живой симуляцией и не вызывают reload/save-on-resume. Checkpoint фиксируется на command/wave transitions, а не на каждом фоновом callback.

Battle checkpoint orchestration:

- успешный Place/Upgrade/Sell → попытка save текущей Preparation;
- Start Wave → обязательный save текущей Preparation до Domain transition;
- наблюдаемый переход Combat → WaveComplete/Victory/Defeat → save уже начисленного результата;
- успешный ContinueToNextWave → save новой Preparation;
- rejected commands/Cancel → нет save;
- загрузка WaveComplete/terminal не вызывает Step или transition и не начисляет награды.

Views создаются из восстановленных Towers; enemies/selection/confirmation/beams не переносятся. Save Status Text показывает успех/backup/write diagnostics. UI не изменяет Gold, HP, Grid или TowerState напрямую.

## MainMenu uGUI contract

Сохраняются uGUI, `CanvasScaler` 1920×1080 и текущий graybox-стиль. MainMenu содержит ровно один EventSystem/GraphicRaycaster, заголовок VEILWARD, New Game Button, Continue Button и Status Text. Continue interactable только после успешной проверки primary/backup и фазы Preparation или WaveComplete. Victory/Defeat дают сообщение о завершённом матче и не запускают Continue.

New Game и Continue используют реальные `Button.onClick` listeners, снимаемые в `OnDestroy`. Battle и MainMenu references генерируются через Editor builder и проверяются validator; ручные YAML substitutions не используются.

## Regression и evidence

REG-BATTLE-067…088 фиксируются до реализации. EditMode покрывает round-trip после Build/Upgrade/Sell, rejected/Cancel, interrupted-wave rollback, WaveComplete/Next Wave/terminal, repeated loads, deterministic continuation, ID monotonicity/exhaustion, invalid snapshots, schema/content mismatch, corrupt/truncated files, backup fallback, atomic replace, write failure и failed New Game reset с последующим Continue. PlayMode использует temporary save root и реальные Button.onClick для MainMenu → Battle → checkpoint → scene reload/MainMenu → Continue; отдельно проверяются recreated views и cleared selection.

В `Docs/review/P1.5b/` сохраняются landscape кадры MainMenu, Preparation после restore и WaveComplete/terminal по фактически выполненному сценарию, `qa.log`, Console audit и sanitized `checkpoint-example.json`. Физический force quit/relaunch на iPhone, signing, Simulator, safe area, built-player touch и Unity CI отмечаются NOT VERIFIED / BLOCKED без фактических запусков.

```bash
./Scripts/run-static-checks.sh
```
